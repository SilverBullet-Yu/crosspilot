## P0｜知乎内容是否可用且有增量　状态：接近通过（3.5/4）

- [x] 查阅当期赛事技术指南及平台条款，确认官方查询入口、申请方式、配额、返回字段。**已核实。** 入口 <https://developer.zhihu.com/docs>；Bearer 鉴权 + `X-Request-Timestamp`；Secret 自助生成于 <https://developer.zhihu.com/profile>。
  **⚠️ 配额以实测为准，与手册严重不符（2026-11-18 `quota` 实测本账号当日）：知乎搜索 `TotalQuota=10`（手册称 5000）、热榜 2（手册称 100）、直答 2（手册称 100）、全网搜索 10（手册未写明）。详见 `CrossPilot_证据_dim04_知乎实查记录.md` 4.0 节。**
- [x] **「能查询不等于能建库」已分别核实。** 摘录展示：可行。内容留存：仅限「摘要+链接+时间」级引用，接口不返回正文全文（`ContentText` 字段定义为「内容摘要」，`Count` 上限 10，`HasMore` 固定 false）。模型处理：可行，受直答额度约束。**建全文库/向量库：不可行**——接口无全文无遍历，手册明文「严禁批量爬取、滥用站内用户数据」，官方知识库 API 只接受本地文件 multipart 上传，不提供搜索结果入库接口。
- [x] 用「旅行收纳包／出海卖点 × 容量／便携」实查，记录检索词、日期、来源链接和相关片段。**已完成（2026-11-18，CLI v0.6.3，消耗 3 次搜索额度）。** 三组检索词：`旅行收纳包 容量 便携`、`亚马逊德国站 收纳包 详情页 卖点`、`出海 德国 消费者 产品卖点 差异 文化`。共取得 5 条相关片段，均附原文链接、AuthorityLevel、赞同数与时间戳，并逐条标注「能说明什么／不能说明什么」。
  **方法论发现：30 条结果中，同时覆盖「德国 + 收纳包 + 容量」的条目为 0 条。** 中文语料里有大量面向中国用户的收纳包测评，也有大量面向卖家的德国市场通论，但两者交集为空——这实证了方案 1.1 所述的「来源分散、证据口径不统一」。
- [ ] 提取至少一个能改变核查方向的问题，并让运营确认是否有用。**问题已提出，运营确认待 P0-3。**

**已提出的三个核查问题**（均标为「问题来源」，不计为德国消费者证据）：

1. **核心问题**：原假设是「大容量应放首屏」，但中文从业经验普遍认为德国消费者「重视清晰的产品参数、决策理性」。那么首屏该放的，是否是**精确的尺寸/容量参数 + 可核验的合规标识**，而非「大容量」这个形容性卖点？——此问改变的是核查对象本身。
2. **权衡问题**（对应清单原举例）：有中文语料指出「大容量款装满后臃肿，商务场合观感不利落」。容量带来的装载收益是否会被携带观感抵消？德国站主力场景是商务短差还是休闲旅行？
3. **框架问题**：若德国消费者确实更重视退换货政策与合规标识，则**首屏信息的竞争对手可能不是其他产品卖点，而是信任要素**——「容量 vs 便携」这个对比框架本身可能选错了维度。

**新增高优先级风险：演示额度。** 若 10 次/天即为赛事期间实际额度，现场 Demo 极易耗尽（排练一次 + 评委体验两三次即用完）。必须做：① 检索结果本地缓存；② 演示前预跑并留存结果；③ 额度耗尽时的明确降级提示（手册提交前检查第 7 条即要求此项）。**待确认**：当前额度是否为未参赛账号默认值、参赛后是否随 Token 补贴提升——建议直接询问官方助手。

**方案影响：** 原方案 5.1 的「可选 pgvector / ChromaDB」用于知乎侧的设想需改写为「实时检索 + 摘录引用 + 链接回源」；向量库对象仅限用户上传的授权资料。可补偿的收益：搜索 API 原生返回 `AuthorityLevel`（权威等级）与 `RankingScore`，可直接用作证据卡的来源质量标注，此前未被方案利用。
