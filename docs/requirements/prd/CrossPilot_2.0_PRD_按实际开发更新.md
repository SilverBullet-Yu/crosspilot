## 0. 文档结论与状态口径

### 0.1 一句话结论

CrossPilot 2.0 当前是一个**面向黑客松演示与评估方法验证的可运行 Web MVP**：固定“旅行收纳包 → 德国市场 → 详情页首屏卖点验证”场景，以知乎中文从业经验为 L2 侧、EU Safety Gate 监管语境为 L3 侧，结合证据卡契约、L1-only 判定门禁、近重复去重、规则立场基线与人工复核、Wilson 95% 区间和四值状态机，展示“假设 → 证据 → 判定 → 待验证问题”的证据链。判定已按 `claim_id` 分卖点执行，支持德国 L1 评论的本地导入、人工立场覆盖、不相关评论与相关但未归属评论独立保留，并能把 L1/L2 跨来源差异转成带出处的问题。

项目**尚未形成真实德国消费者一手反馈驱动的完整商业闭环**。`real` 场景的德国 L1 仍为零样本；Amazon.de 公开评论候选因平台使用条件禁止未经书面许可的系统性提取、数据挖掘与商业再利用而否决，自动提取原文与元数据已删除。真实 L1 只接受品牌授权导出或 Amazon 书面许可，运营试用尚未执行。新增 readiness 审计当前返回 `blocked`，明确禁止把演示、待复核或探索性样本当作真实案例完成。产品无服务端任务创建/保存、账号系统或数据库持久化；已有本地自定义假设、假设级验证轮次与文件归档。评论导入为本地 CLI/快照模式，不提供无鉴权的在线上传；真实 L1 强制提供 `authorization_ref` 与至少覆盖 `internal_product_validation` 的 `authorization_scope`，缺少授权依据时拒绝导入；原始 `review_id` 原样保留到快照、API 与卡面。快照记录输入文件与内容 SHA-256、冲突拒写，`data/snapshots/l1/` 默认不入公开仓库。

### 0.2 状态定义

本文统一使用以下状态，避免把“已经写好代码”“有测试”“真实数据已接入”“业务闭环已完成”混为一谈。

| 状态 | 含义 |
|---|---|
| **已实现并验证** | 有对应生产代码，且在本次核对中由自动化测试或构建/页面断言验证 |
| **部分实现** | 核心子模块存在，但未接入生产主链路，或只覆盖演示/部分数据/部分市场 |
| **适配层就绪，待实测** | 已实现接口、校验、失败语义和离线测试，但本机缺少凭据，未完成真实第三方调用验收 |
| **未实现** | 当前生产代码没有对应能力，不能作为已交付功能描述 |
| **计划中** | 原 PRD 或路线图中的候选能力，不在当前交付范围 |

### 0.3 真实案例完成口径

`audit_case.py` 与 `/api/case/readiness` 是“真实商品案例 + 运营试用”的唯一就绪度门禁：

| 级别 | 含义 | 能否称为真实案例完成 |
|---|---|---|
| `blocked` | 缺少合规德国 L1、关键溯源字段或演示卡混入 | 否 |
| `exploratory` | 已有 L1，但未归属、待复核或任一卖点 `n<30` | 否，只能探索 |
| `decision_ready` | 数据、复核与样本门禁通过，尚缺运营确认 | 否，仅可讨论样本内判定 |
| `trial_complete` | 每条卖点至少一轮 `real` 场景已确认运营记录，引用真实 `review_id: source_url`，且绑定当前 L1 快照 | 真实案例与试用闭环完成，但仍不可外推总体市场效果 |

当前实测为 `blocked`，CLI/API 返回 `snapshot_sha256` 与 `rounds_archive_sha256` 绑定消费者证据及运营轮次版本；CLI `--claim-id`、API 重复 `claim_id` 与历史页输入可指定活跃卖点，自定义-only 案例不被未活跃内置三项阻塞。`--require-ready` 只接受后两级；`--require-trial-complete` 仅接受 `trial_complete`，用于真实案例 + 运营试用闭环验收。相关 L1 的人工复核必须同时满足 `classification_method=manual`、`review_required=false` 和非空 `classification_note`，规则低优先级与 LLM 不得绕过。L1 快照损坏或归档哈希不匹配返回 HTTP 409。该门禁校验的是本地真实 L1 快照与归档轮次，不会把浏览器本地草稿、模拟评论或测试夹具计入完成。

## 1. 产品定位

### 1.1 当前定位

**CrossPilot 是面向出海卖点的“证据核验工作台”原型，而不是自动生成市场结论的报告工具。**

当前产品帮助用户完成：

1. 选择一个预置的产品卖点假设；
2. 查看与假设相关的中文从业经验、监管背景或显式演示评论；
3. 识别支持、相反、缺失和未归属证据；
4. 在证据不足或冲突时获得可追溯的判定依据；
5. 获得待验证问题、访谈问题和 A/B 测试草稿；
6. 通过人工判断和项目外验证日志记录下一步动作。

当前产品不负责替用户决定“德国消费者一定喜欢什么”，也不自动完成投放、上架或营销执行。

### 1.2 固定业务边界

| 维度 | 当前边界 |
|---|---|
| 商品 | 非电器旅行收纳包 |
| 目标市场 | 德国；后端 `market` 固定为 `de` |
| 渠道 | 商品详情页首屏、卖点表达和初步测试方向 |
| 企业假设 | 前端预置容量越大越好、功能越多越好、低价是核心购买理由；另支持按场景保存本地自定义假设与 `claim_id` |
| 中文侧 | 知乎从业者经验，L2；只用于形成问题，不直接支撑偏好结论 |
| 海外真实侧 | EU Safety Gate 近邻品类监管记录，L3；不是消费者评论 |
| 德国消费者侧 | **真实 L1 为零样本** |
| 正负反馈对照 | 目前通过 conflict / limited 两个显式演示场景展示，不是德国真实用户数据 |

### 1.3 产品形态

当前代码中的产品形态为多页工作台式 Web 应用：

| 页面 | 路由 | 当前能力 |
|---|---|---|
| 产品概览 | `/` | 产品叙事、模拟示例、四步方法、样本量/票数交互判定演示器、FAQ、工作台入口 |
| 卖点验证工作台 | `/workbench` | 场景切换、产品关键词检索、判定横幅、假设证据分组、证据卡、知乎 L2 附录、结构化 L1/L2 对照、待验证问题和测试建议；可复制计划、导出 JSON 案例证据包或导出待补齐的授权 L1 导入模板 |
| L1 人工复核 | `/review` | API 模式加载真实授权 L1，逐条修正立场/归属/相关性，支持卖点筛选、关键词搜索与逐卖点进度，本机保存草稿、导出可回导 JSON；fixtures 模式不伪造复核数据 |
| 历史验证项目 | `/history` | 本地轮次与运营试用总结回看/导出；API 模式展示真实案例 readiness 门禁，可指定活跃卖点审计范围 |

## 2. 目标用户与待验证需求

### 2.1 目标用户

首要目标用户仍为：

- 准备向德国市场推出或迭代消费品的中国中小品牌；
- 负责 Listing、商品内容、海外运营和市场调研的团队；
- 缺少本地消费者研究能力，但能提供合法、脱敏业务资料的团队。

该用户定义来自原项目方案，尚未由本项目代码或用户访谈数据独立验证。

### 2.2 当前要解决的问题

当前版本聚焦一个更窄的问题：

> 当团队还没有可靠的德国消费者反馈时，如何避免把中文经验、监管信息或少量演示反馈误当成“海外用户偏好”，并清楚知道下一步该补什么证据？

这是一个**证据纪律和决策透明度问题**，不是自动市场预测问题。

### 2.3 尚未验证的商业假设

以下内容仍属于假设，不应写成已经证实的事实：

- 跨境品牌是否普遍存在“卖点未经当地反馈验证就上线”的流程缺口；
- 该缺口是否高频、高价值到足以产生付费；
- 用户是否愿意为单次核验支付 ¥99—199；
- 现有工具是否无法满足该需求；
- 中文从业经验是否具有可持续、可规模化的商业价值。

## 3. 竞品定位与差异化边界

原 PRD 的竞品方向保留，但当前项目没有完成系统的竞品实测，不应将定位表述为已经建立的技术护城河。

| 比较对象 | 当前可声称的差异 | 不能声称的内容 |
|---|---|---|
| Accio 等贸易/选品工具 | CrossPilot 围绕企业已有卖点建立证据核验，而非供应商探索或贸易执行 | 不能声称对方没有生成、上架或研究能力 |
| Helium 10 / SellerSprite 等 Listing 工具 | CrossPilot 将“生成卖点”前移到“验证卖点是否成立” | 不能声称现有工具没有评价分析或 Listing 优化能力 |
| ITC Export Potential Map | CrossPilot 面向具体商品、具体市场和具体卖点 | 不能用其宏观贸易数据替代消费者偏好结论 |
| 通用大模型 | CrossPilot 强调来源回链、证据分层、去重、门禁、区间和冲突保留 | 不能声称大模型不能生成报告或引用 |

当前可 defensible 的差异是**证据治理方法**：L1-only 判定、L2/L3 旁路、去重先于计数、统计门禁、显式不足和显式冲突。该差异的商业价值仍待用户验证。

## 4. 为什么使用知乎

### 4.1 当前产品职责

知乎在当前系统中承担 **L2 中文从业经验源**：

- 提供跨境从业者的经验、观点和待讨论问题；
- 为德国 L1 尚未到位时的问题发现提供素材；
- 通过回源链接保留来源，而不是建立全文库；
- 不直接进入消费者偏好判定。

### 4.2 已实现的合规处理

知乎适配器已实现：

- Bearer Token 与秒级时间戳请求头；
- 单次检索数量上限 10；
- 摘录长度不超过 300 字符；
- 先剔除邮箱/电话，再截断摘录；
- 作者昵称不保留，仅生成不可逆派生 ID；
- L2 卡立场归一为 `insufficient`；
- 鉴权失败、限流、网络异常和响应结构异常分别抛出；
- live 模式配额耗尽或网络失败转为 `l2_notice`，不静默返回“正常空结果”；
- snapshot 与 live 双路径。

### 4.3 当前限制

- 本机没有知乎 Access Secret，**live 端点响应结构未经过真实凭据调用核验**；
- 实测搜索额度为 10 次/日，与早期手册值存在显著差异；
- 当前真实快照只有“旅行收纳包”一个查询词、3 张真实摘录卡；
- 未预跑的查询词会触发快照缺失提示；
- 没有自动批量发帖、知识共创发布或企业材料回传功能。

## 6. 已实现的核心用户流程

### 6.1 本地夹具演示流程（默认模式）

1. 用户打开产品概览 `/`；
2. 点击“开始验证”进入 `/workbench`；
3. 选择真实快照、演示冲突或演示有限支持场景；
4. 前端从 `apps/web/fixtures/` 读取同源夹具；
5. 后端不参与页面渲染，现场网络与知乎配额不影响演示；
6. 工作台展示判定、假设证据和下一步问题。

### 6.2 真实 API 快照流程

1. 后端启动时预热 Safety Gate 本地数据；
2. 前端通过 `NUXT_PUBLIC_API_BASE` 指向 FastAPI；
3. `GET /api/evidence?query=...` 执行双语查询扩展；
4. Safety Gate 返回 L3 语境卡，知乎快照返回 L2 卡；
5. 判定管道只接收 L1；当前没有 L1，因此输出 `insufficient / no_l1`；
6. 前端展示黄色“缺少有效数据”状态、L3 卡、L2 卡和待验证问题。

### 6.3 演示反馈流程

1. 用户切换到 conflict 或 limited 场景；
2. 请求 `GET /api/evidence/demo?scenario=...`；
3. 后端生成 34 张或 30 张显式 `is_demo_data=true` 的德语模拟评论；
4. 去重、门禁、Wilson 区间和四值判定照常运行；
5. 前端以斜纹/角标/分隔条明确标记演示数据，不与真实反馈混排；
6. 该流程验证的是**产品交互与判定方法**，不是德国市场事实。

### 6.4 当前不存在的人工回填流程

原 PRD 中“用户回填访谈或 A/B 测试结果，保存本轮结论变化”没有产品实现。当前 `docs/demo/validation_log.md` 是人工维护的项目文档，不是系统内的实验回填功能。

## 9. 证据模型与判定规则

### 9.1 证据层级

| 层级 | 当前定义 | 当前代表来源 | 是否可单独支撑偏好结论 |
|---|---|---|---|
| L1 | 目标市场一手消费者反馈 | 演示评论；未来品牌授权德国导出 | 可以，但仍需过门禁和区间判定 |
| L2 | 中文从业者经验、二手转述 | 知乎 | 不可以，只形成待验证问题 |
| L3 | 宏观统计、监管和市场语境 | EU Safety Gate、Eurostat、Comext、GDELT、OpenAlex | 不可以，只作背景或问题线索 |

**层级名称不是市场真实性的保证。** 当前演示卡虽然标为 L1，但 `is_demo_data=true`，不能作为真实德国证据。

### 9.2 证据卡必现字段

| 字段 | 当前约束 |
|---|---|
| `excerpt` | 非空原文摘录 |
| `source_url` | URI；前端渲染回源链接 |
| `language` | 如 `de`、`en`、`zh-CN` |
| `published_on` | ISO 日期；不以采集日冒充发布日期 |
| `level` | `L1 / L2 / L3` |
| `sample_size` | 整数或 `null`；未知时前端需提示偏差风险 |

可选字段：

- `stance`：卡级输入信号，`support / oppose / insufficient`；
- `is_demo_data`：是否演示数据；
- `dedup`：簇 ID、簇大小、是否代表卡；
- `stance_votes`：规则票与 LLM 票；
- `annotator_agreement`：标注器是否一致；
- `grade` / `downgrade_reasons`：当前 schema 已预留，生产卡当前未实际填充 GRADE 结果。

判定级字段属于整个响应包络，不属于单张证据卡。

### 9.3 判定管道

当前后端规则固定为：

```text
输入卡
  → 仅保留 L1
  → 对 L1 摘录近重复去重
  → 只统计每簇代表卡
  → 统计 support / oppose / insufficient
  → 以 support + oppose 的簇数为分母
  → 样本量门禁
  → 分别计算 support / oppose 的 Wilson 95% 区间
  → 映射四值状态
  → 输出去重摘要、区间、门禁和功效注记
```

### 9.4 四值状态

| 状态 | 当前规则 |
|---|---|
| `supported` | 过门禁，且支持份额 Wilson 95% 下界 `> 0.5` |
| `refuted` | 过门禁，且反对份额 Wilson 95% 下界 `> 0.5` |
| `conflicting` | 过门禁，双方票数均大于 0，且两个份额区间重叠 |
| `insufficient` | 无 L1、无极性样本、样本低于门禁，或不能形成上述结论 |

门禁状态另外记录：

- `no_l1`
- `no_polarized`
- `below_minimum`
- `pass`

### 9.5 统计口径

- 最小去重后有极性样本量：**30**；
- `insufficient` 卡不进入 Wilson 分母，单独报告数量；
- `n=30` 时，约 68% 的决定性份额才能使 Wilson 下界超过 0.5；
- 21:9 → `supported`，支持区间约为 `[0.521, 0.833]`；
- 15:15 → `conflicting`；
- 20:10 → 当前实现为 `conflicting`，不是 `insufficient`；
- 0:30 → `refuted`；
- 30 条相同评论复制 → 去重为 1 簇 → 门禁拦下，不能判支持。

### 9.6 当前判定链的未接入部分

规则立场基线已接入授权 L1 导入，并支持人工 `stance` / `stance_note` 覆盖；填写 `stance` 时 `stance_note` 必填，缺失或清洗后为空拒绝导入。最终立场、规则票、一致度与分类方法进入快照、API 和卡面。预置卖点规则票先选择命中该卖点术语的从句，避免跨卖点极性串票；自定义卖点可在授权 JSON 顶层用 `claim_terms` 声明术语范围，范围进入快照哈希、API `aspect_terms` 与复核回导 JSON。未命中、未归属或未声明术语的自定义卖点回退整条票并强制人工复核，相关从句占比与命中术语写入 `review_reasons`。同一卖点精确/近重复评论出现跨立场标签时，不合并、不自动改票，标记 `review_required=true` 并列出冲突 `review_id`，避免假分歧。规则结果按保守阈值分流：仅强支持可低复核优先级，其他结果建议人工复核；MARC 低优先级覆盖 5.9%、准确率 92.4%，但金标是整体星级而非卖点级标签，卖点级规则也未独立评测，不能视为模型准确性证明。LLM 适配器和两票聚合器仍有代码与测试，但 LLM 未凭据实测、未启用为生产主分类器。

因此当前应表述为：

> 判定、去重和统计链已在演示输入上验证；授权 L1 的规则分类与人工复核已接入，LLM 分类与两票聚合尚未进入生产主链路。

| OpenAlex | L3 文献元数据 | 2,454 行 | 方法参考 | 每主题前 500 条，不是文献普查 |
| GDELT | L3 媒体语境 | 1,090 行 | 数据资产 | 覆盖仅 2021H1–2022H2，时间覆盖 15.1%；禁止趋势和量级推断 |
| Amazon Reviews 2023 | L1 性质，美国市场 | 6,146 行 | 管线试点、分层采样 | 仅 Subscription Boxes 分片；不是德国数据，不是旅行收纳包数据 |
| GERestaurant | 评测基准 | 3,078 条 | 规则立场基线评测 | 餐厅域，不可外推商品域 |
| MARC | 评测基准 | 10,000 条 | 商品域立场基线评测 | 研究许可，禁再发布，商业化需下线；不进证据卡 |
| USAGE/Bielefeld | 标注基准 | 1,233 条评论汇总 + 25,292 span | 标注层评测 | 公开件不含评论文本，不能当消费者证据卡 |
| 知乎快照 | L2 | 3 张真实摘录卡 | 工作台中文侧附录 | 仅一个查询词；live 未凭据核验 |

数据区有三种常见合计口径（见 `data/sources/README.md` §2.0）：

- **67,565 行**：全部 CSV 行，10 张主表实际行数之和；
- **66,332 行**：主表口径，排除 USAGE 评论汇总表（1,233 行，与 span 表一对多）；
- **42,273 行**：记录/评论级，排除 USAGE 的 25,292 行 span 标注。

三种口径不应混写为同一个“数据总量”。

### 10.4 德国 L1 缺口

当前没有任何可用于德国旅行收纳包偏好判断的真实消费者一手反馈：

- Amazon Reviews 2023 是美国站，且无 marketplace/language 字段可筛德国子集；
- GERestaurant 是餐厅域基准；
- MARC 是研究基准且不含旅行收纳包目标市场语境；
- Safety Gate 是监管记录；
- 知乎是从业经验；
- 演示评论是项目自撰模拟数据。

因此当前真实场景只能输出：

```text
stance = insufficient
gate_status = no_l1
n_l1 = 0
```

这是当前产品最重要的业务事实，也是下一阶段最高优先级输入。

## 12. 非功能需求与合规边界

### 12.1 数据许可

当前注册表将数据源分为可商用、需凭据、研究限定和禁转售等类别。已实现统一闸门：

- 未登记数据源拒绝加载；
- 商业模式下 `commercial_ok=false` 的来源拒绝使用；
- 需要凭据的来源禁止匿名调用；
- 卖家自撰内容不得进入消费者证据侧；
- 非 L1 不得单独支撑消费者偏好结论；
- 明确排除 OpenSubtitles；
- MARC 商业化启动即下线；
- Comtrade 禁止匿名 preview；
- DeepL Free 禁止传入含个人数据文本。

### 12.2 隐私与个人信息

- 知乎摘录先剔除邮箱和电话，再截断；
- 作者昵称不保留；
- 不建立知乎全文库；
- LLM 输入仅接受不超过 300 字符的已清洗摘录；
- LLM 输出必须提供原文连续片段，否则视为编造并失败/回退；
- 当前没有企业文件上传，因此企业资料的存储隔离和删除流程尚未实现。

### 12.3 失败语义

| 情况 | 当前行为 |
|---|---|
| 前端后端不可达 | 显示加载失败和重试按钮 |
| 知乎快照缺失/损坏 | L2 区域显示 `l2_notice`，不静默伪装正常 |
| 知乎鉴权失败 | 显式提示检查 Access Secret |
| 知乎限流 | 显式提示实测额度和 snapshot 降级建议 |
| 证据卡缺必现字段 | 拒绝渲染该卡，显示契约占位说明 |
| 关键词未命中假设 | 进入“未归属证据”，需人工复核 |
| LLM 配置缺失 | 适配层响亮失败，不静默假装 LLM 可用 |
| LLM 运行失败 | 适配层回退规则基线并记录 `fallback_used` 和原因 |
| Safety Gate 启动预热失败 | 不拖垮启动，但查询时重新尝试并抛出真实异常 |

### 12.4 当前安全与生产缺口

- 无账号和权限系统；
- 无多项目/多租户隔离；
- 无 API 鉴权；
- 无速率限制；
- 无生产数据库；
- 无审计日志；
- 无数据保留/删除策略；
- 无 Secrets 管理平台；
- CORS 仅限本机开发前端；
- 尚无证据证明可承载真实企业敏感资料。

| 实现项目隔离 | 不同用户/项目的数据不可越权访问 |

### 15.3 P2：提高自动化与规模化

| 事项 | 当前边界 |
|---|---|
| 知乎 live 首跑核验 | 需 Access Secret；响应结构以实际结果为准 |
| LLM 双域实测 | 需 OpenAI 兼容端点；达到验收线后才能启用 |
| NLI 卡片↔假设归属 | 新数据以显式 `claim_id` 为准；旧数据/演示卡缺少 ID 时才回退关键词，NLI 未实现 |
| 语义检索 | 当前为 CSV 子串检索；是否引入向量库需另行评估 |
| 多产品、多市场 | 后端市场仍固定德国；本地自定义假设已实现，但没有服务端项目模型 |

| GRADE 自动分级 | 当前仅有 schema 字段和叙事，未实现自动质量评级 |

### 15.4 明确不做

当前阶段仍不做：

- 自动销量预测；
- 自动广告投放；
- 自动上架和营销执行；
- 全平台评论抓取；
- 法务、税务或海外认证；
- 无授权跨境采集个人数据；
- 用美国数据冒充德国消费者结论；
- 将少量演示评论上升为全国性偏好；
- 为“多 Agent”而引入无实际价值的编排层。

## 16. 用户访谈与评估计划

### 16.1 访谈目标

当前最优先的不是继续增加页面，而是验证：

1. 目标用户是否确实有“卖点未经当地反馈验证”的任务；
2. 没有 L1 时，当前输出是否仍有助于决策；
3. 用户是否愿意提供合法、脱敏的德国站反馈；
4. 用户更看重证据链、问题清单还是报告交付；
5. 单次验证的真实付费意愿和替代成本。

### 16.2 建议 Go / No-Go

- 至少 5 位受访者能描述近期真实任务；
- 至少 3 位愿意提供合规资料测试；
- 至少 2 位认为当前输出比现有方法更有助于决策；
- 如果无法取得合规德国 L1，或用户认为该任务低频/低价值，应停止扩展平台能力，转向更窄的交付服务或另一个可量化场景。

**数据边界复核：** `amazon_reviews_2023` 的美国站试点受 manifest 的 `tier_caveat` 约束，**不得写入德国市场偏好结论**；该数据只能用于管线验证和方法演练。

### 16.3 当前可评估指标

| 指标 | 建议方法 | 当前状态 |
|---|---|---|
| 证据卡字段完整率 | 全量卡检查六字段 | 已自动化 |
| L2/L3 误用率 | 检查是否进入偏好判定 | 已自动化 |
| 重复评论膨胀率 | 构造重复/变体样本 | 已自动化 |
| 判定边界一致性 | 对照后端与前端公式用例 | 部分自动化 |
| 引用准确率 | 人工抽查 30 条来源与摘录 | 待开展 |
| 假设归属准确率 | 人工核对关键词分组 | 待开展 |
| 真实 L1 判定有效性 | 品牌授权样本端到端评估 | 阻塞于数据 |
| 完成时长 | 对比人工与工具流程 | 待开展 |
| 复用与付费意愿 | 用户访谈和真实报价测试 | 待开展 |

## 17. Demo 与路演口径

### 17.1 推荐演示顺序

1. 在产品概览解释“卖点验证，不是卖点生成”；
2. 进入 `real` 场景，先展示“德国 L1 仍为零样本，公开评论候选因平台条款否决，系统拒绝给偏好结论”；
3. 展示 Safety Gate L3 与知乎 L2 的来源分层；
4. 打开一条假设，展示独立黄色空状态；
5. 展示待验证问题、访谈问题和 A/B 草稿；
6. 切换到 `conflict`，解释去重、Wilson 区间和四值状态；
7. 切换到 `limited`，解释 21:9 与 0.521 下界；
8. 明确说明 conflict/limited 是演示数据，不是德国真实反馈；
9. 说明下一步是品牌授权 L1、任务持久化和真实评测。

### 17.2 推荐答辩表述

- **解决谁：** 缺少德国本地消费者研究能力、正在调整出海卖点的中小品牌团队。
- **为什么买：** 减少无依据卖点决策，并明确下一步需要补哪些证据；该付费价值仍待验证。
- **为什么不是普通报告工具：** 系统保留证据层级、来源、去重、门禁、区间和冲突，证据不足时不硬判。
- **为什么是知乎：** 中文从业经验是 L2 问题来源，不代表德国消费者，也不直接决定偏好。
- **当前最大缺口：** 德国 L1 一手反馈为零，真实端点是诚实的 `insufficient`。
- **当前成熟度：** 可运行演示和方法验证 MVP；不是完整商业 SaaS。

## 20. 当前交付定义

满足以下条件，可以认为当前黑客松演示版本交付完成：

- 后端 367 项测试及数据区六道校验通过；
- 前端生产构建和 97 项 SSR 断言通过；
- 产品概览、工作台三场景、历史页本地轮次/运营总结与 readiness 门禁可访问；
- `real` 场景明确显示德国 L1 不足，readiness 返回 `blocked`；
- `conflict` 和 `limited` 场景明确显示演示数据；
- 判定链路可追溯到门禁、去重和 Wilson 区间；
- 对外材料不声称德国真实消费者结论；
- 对外材料不声称服务端任务保存、服务端反馈回填、服务端报告或数据库已实现；本地案例证据包与轮次 JSON 导出不计为服务端能力。

满足以下条件，才可称为真实业务闭环版本：

- 合规德国 L1 数据接入，并通过溯源、模拟隔离与人工复核；
- 每条卖点去重后有极性样本达到 `n≥30`；
- 规则立场分类与人工复核进入生产管道；授权 L1 可通过 `--dataset l1` 使用人工复核金标逐卖点评测规则或 claim-aware LLM，当前尚无真实评测结果；LLM 与两票聚合完成真实评测后再启用；
- 每条卖点至少完成一轮 `real` 场景运营确认并归档，引用真实 `review_id: source_url`，填写 `market=de` 且 `l1SnapshotSha256` 与当前快照一致，readiness 达到 `trial_complete`；
- 用户能创建、保存和回填任务；
- 结果可导出、可审计、可隔离；
- 完成真实用户访谈与效果评估；任何就绪级别都不得直接声称总体市场效果。
