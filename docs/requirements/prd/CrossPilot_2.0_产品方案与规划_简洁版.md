# CrossPilot 2.0 产品方案与规划

> 简洁版｜核对日期：2026-11-28
> 依据：当前代码、数据与测试结果

## 一、产品画像

**CrossPilot 是一个“出海卖点证据核验工作台”。**

它帮助准备进入德国市场的中国消费品牌，在详情页上线前回答一个问题：

> **这个卖点是否有真实用户证据支持，下一步应该验证什么？**

产品不生成“德国消费者喜欢什么”的笼统结论，而是把企业假设、中文从业经验、监管背景和消费者反馈放在同一证据链中，明确区分：

- **已有有限支持**
- **多数反馈反对**
- **样本内存在分歧**
- **缺少有效数据**

### 目标用户

- 准备向德国市场推出或迭代消费品的中小品牌；
- 负责 Listing、商品内容和海外运营的团队；
- 缺少本地消费者研究能力，但能提供合法业务资料的团队。

### 当前业务边界

| 项目 | 当前范围 |
|---|---|
| 商品 | 非电器旅行收纳包 |
| 市场 | 德国 |
| 场景 | 商品详情页首屏卖点验证 |
| 假设 | 预置容量越大越好、功能越多越好、低价是核心购买理由；支持本地自定义假设 |
| 输入 | 产品关键词，或显式演示数据 |
| 输出 | 证据卡、四值判定、待验证问题、访谈问题、A/B 测试方向 |

### 核心工作流

```text
提出卖点假设
  → 检索证据
  → 区分 L1 消费者反馈 / L2 中文经验 / L3 监管背景
  → 去重并判定
  → 输出证据状态
  → 给出下一轮验证任务
```

### 差异化

普通工具侧重“生成卖点、优化 Listing、寻找供应商”，CrossPilot 侧重**验证卖点是否成立**：

1. **证据分层**：知乎经验和监管数据不能冒充消费者偏好；
2. **来源可追溯**：每条证据保留摘录、链接、日期、语言和样本量；
3. **判定可量化**：去重后样本不少于 30，使用 Wilson 95% 区间判断支持、反对或冲突；
4. **拒绝硬判**：没有可靠 L1 消费者反馈时，明确输出“证据不足”；
5. **保留矛盾**：支持与反对证据并排展示，不强行调和。

## 二、当前产品能力

### 已实现并验证

| 模块 | 当前能力 |
|---|---|
| 产品概览页 | 产品介绍、方法说明、判定公式演示、FAQ |
| 卖点工作台 | 场景切换、关键词检索、证据分组、判定横幅、区间标尺 |
| 证据卡 | 六字段校验、来源回链、缺字段拒绝渲染、演示数据标识 |
| 数据接入 | EU Safety Gate 近邻品类 519 条；知乎“旅行收纳包”真实快照 3 条；德国 L1 待品牌授权或平台书面许可，必须声明内部验证等用途，快照带 SHA-256、支持版本化回导且默认不入公开仓库 |
| 判定规则 | L1-only 门禁、同立场近重复去重、样本量门禁、Wilson 区间、四值状态、按 claim_id 分卖点判定 |
| 展示规则 | 证据不足独立空状态；支持/反对左右并排；不相关/未归属证据人工复核 |
| 跨来源对照 | 按卖点分列 L1 样本分布与 L2 从业线索，保留双方完整出处；只生成场景核对/潜在分歧问题，不推断 L2 消费者立场 |
| 假设管理 | 三条预置假设 + 本地自定义假设；编辑、核实问题、关键词与 claim_id 按场景保存 |
| 建议输出 | 当前假设的待验证问题、3 个动态访谈问题、原型测试方案、2 版待测试文案 |
| 验证留痕 | 假设级轮次追加观察、决定、理由与下一步；同组原型按参与者/顺序/装载/取物/摩擦点结构化记录；历史页回看、导出，CLI 校验并 SHA-256 归档 |
| 完成门禁 | `audit_case.py`、`/api/case/readiness` 与 `/history` 门禁面板统一审计真实 L1、溯源、模拟隔离、归属、复核、样本和 real 场景运营确认；fixtures 模式不伪造结果，当前为 blocked |
| 证据分类 | 规则基线 + 人工立场覆盖；保留规则票、一致度、分类方法与复核说明；`/review` 支持本机复核草稿与 JSON 回导，授权范围原样锁定不可扩权 |
| 工程验证 | 后端 367 项测试、9 个数据源结构/时间覆盖/质量校验、前端生产构建、97 项 SSR 断言通过 |

### 三个演示场景

| 场景 | 数据 | 结果 | 用途 |
|---|---|---|---|
| 真实快照 | Safety Gate L3 + 知乎 L2；德国 L1 为零 | `insufficient / no_l1` | 证明系统不编造结论 |
| 样本分歧 | 15 支持 + 15 反对 + 2 条重复摘录 + 1 条未归属评论，均为模拟数据 | 商品级 `conflicting`，单卖点均证据不足 | 展示去重、区间、正反对照与未归属保留 |
| 有限支持 | 21 支持 + 9 反对，均为模拟数据 | 商品级 `supported`，单卖点均证据不足 | 展示样本门禁与统计判定 |

### 真实案例完成门禁

`audit_case.py` 与 `/api/case/readiness` 使用同一套四级状态：

| 状态 | 验收含义 |
|---|---|
| `blocked` | 缺少授权德国 L1、关键溯源字段或混入演示卡 |
| `exploratory` | 已有 L1，但未归属、待复核或任一卖点 `n<30` |
| `decision_ready` | L1、溯源、复核与样本门禁通过，尚缺运营确认 |
| `trial_complete` | 每条卖点至少一轮 `real` 场景已确认记录，引用真实 `review_id: source_url`，且绑定当前 L1 快照；仍不得声称总体市场效果 |

当前真实案例实测为 `blocked`，所以原始 idea 中“完成真实商品案例，再请运营试用”仍未验收。

## 三、当前边界与关键缺口

### 最重要的业务缺口

**德国消费者一手反馈（L1）仍为零样本。**

当前真实场景中：

- 德国 L1 尚未取得品牌授权导出或 Amazon 书面许可；
- Amazon.de 公开评论候选因平台条款禁止未经书面许可的系统性提取、数据挖掘与商业再利用而否决，自动提取数据已删除；
- Safety Gate 是监管记录，不是消费者偏好；
- Amazon Reviews 2023 是美国站试点，不能筛出德国子集；
- conflict / limited 场景是显式模拟数据，不是真实市场结论。

因此，当前真实端点只能输出：

```text
claim_id = capacity | features | price
stance = insufficient
gate_status = no_l1
n_l1 = 0 | 0 | 0
```

### 部分实现或尚未实现的产品能力

- 自定义产品与多市场：后端仍固定德国市场；本地自定义假设已实现，但没有服务端项目模型；
- 企业反馈文件：已实现授权 CSV/JSON 的本地 CLI 导入与复核回导，没有 Web 上传接口；
- 任务与历史：已有本地假设级验证轮次、历史回看和 SHA-256 文件归档，没有服务端任务创建或数据库历史；
- 访谈与实验结果：可本地记录观察、决定、理由、下一步和结构化原型观察，没有服务端实验模型；
- 判定结果自动更新：新证据需重新导入/生成响应，没有服务端自动刷新与版本对比；
- 单页报告：已实现案例证据包 JSON 导出，没有 PDF/Word/单页报告；
- PostgreSQL 业务表、ORM 和迁移：未实现，相关依赖与连接配置也已移除；
- 账号、权限、项目隔离和审计：未实现；
- pgvector / ChromaDB 语义检索：未实现。

**结论：当前是可运行、可演示、可审计的证据核验 MVP，不是完整商业闭环。**

## 四、产品规划

### P0：先打通真实德国消费者证据链

**目标：让真实任务能够从品牌授权数据走到可追溯判定。**

1. 获取品牌授权的德国站消费者反馈；
2. 将授权数据导入为 L1 证据卡；
3. 接入规则立场抽取；LLM 实测达标后作为增强分类器；
4. 接入两票聚合，明确标注模型缺席和分歧；
5. 跑通“去重 → 立场 → 门禁 → Wilson 区间 → 四值判定”；
6. 增加“多数反馈反对”的真实样例或独立演示场景。

**验收标准：**

- 每条 L1 卡可追溯到授权数据、时间、市场和来源；
- 不使用美国数据冒充德国证据；
- 无有效数据时仍输出 `insufficient`；
- 每条判定可查看样本数、去重结果、区间和门禁。

### P1：形成可保存、可回填、可交付的工作流

**目标：让团队能够重复使用，而不是只看一次演示。**

1. 建立 Project、Hypothesis、Evidence、EvidenceLink、Experiment、Result 数据模型；
2. 支持自定义产品、市场和卖点；
3. 实现验证历史、重新打开和结果对比；
4. 支持反馈上传和实验结果回填；
5. 新证据进入后刷新判定，并保留旧结论；
6. 导出带来源、判定依据和限制说明的单页报告；
7. 实现账号、项目权限和基础审计。

**验收标准：**

- 用户创建任务后刷新页面仍可恢复；
- 新反馈不会覆盖旧证据和旧结论；
- 不同项目之间不可越权访问；
- 导出的报告可人工复核和分享。

### P2：提高自动化与规模化

| 事项 | 启动条件 |
|---|---|
| 知乎 live 首跑核验 | 获得 Access Secret |
| LLM 双域实测与启用 | 配置 OpenAI 兼容端点，且效果优于规则基线 |
| 语义化卡片↔假设归属 | LLM 凭据可用，完成关键词方案对照 |
| 多产品、多市场 | P0/P1 闭环稳定，且当前固定场景验证完成 |
| 语义检索/向量库 | 数据规模和关键词检索瓶颈得到验证 |
| L3 关联问题生成 | 明确旁路规则，绝不进入消费者偏好判定 |

## 五、用户验证与商业化

### 优先验证

1. 目标用户是否存在“卖点未经当地反馈验证就上线”的真实任务；
2. 没有 L1 时，当前证据工作台是否仍有决策价值；
3. 用户是否愿意提供合规、脱敏的德国站反馈；
4. 用户更需要证据链、访谈清单，还是可直接交付的报告；
5. 单次验证的真实付费意愿。

### Go / No-Go

- 至少 5 位用户能描述近期真实任务；
- 至少 3 位愿意提供合规资料测试；
- 至少 2 位认为输出比现有方法更有助于决策；
- 如果无法获得德国 L1，或需求被验证为低频、低价值，则缩小服务范围或调整方向。

### 商业边界

- 当前没有真实付费验证，不承诺收入；
- ¥99—199/次只能作为访谈定价假设；
- 商业化前必须完成德国 L1 接入、数据许可复核、MARC 下线、人工审核、任务持久化和权限隔离。

## 六、近期执行顺序

| 顺序 | 事项 | 产出 |
|---|---|---|
| 1 | 获取德国品牌授权反馈 | 可追溯 L1 数据集 |
| 2 | 导入 L1 并接入立场抽取 | 真实证据卡和立场 |
| 3 | 完成真实判定演练 | 去重、区间、门禁和结论链 |
| 4 | 访谈 5—10 位目标用户 | 场景、价值与付费反馈 |
| 5 | 实现任务与历史持久化 | 可重复使用的工作台 |
| 6 | 实现反馈回填与报告导出 | 最小商业交付闭环 |

**一句话路线：先用真实德国 L1 证明判定有效，再用持久化与回填形成可交付产品，最后扩展自动化。**
